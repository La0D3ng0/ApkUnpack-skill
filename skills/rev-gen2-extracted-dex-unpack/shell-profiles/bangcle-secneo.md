# 梆梆加固（Bangcle / SecNeo）：二代 `fdex` 抽取型壳

本文归纳**已遇到的 `fdex` 变体**，供下次定位加解密边界使用。壳家族命中只能提示调查方向；另一版本可能改用不同容器、算法或回填方式。具体密钥、地址、RVA、段数和长度必须从当前 APK 重新取得。

## 1. 找容器和真实方法体

先对原始 APK 的 `classes.dex` 运行 [`container_triage.py`](../container_triage.py)。比较 DEX 头部的 `data_off + data_size` 与 `file_size`，检查尾部 overlay 中的 `dexdata0`、内部候选 `fdex` 标记及 EOF 尾标。它们只能提示容器边界；跟踪 Native 对这些标记的读取和段表解析，核实 payload 起点、各段起点、`file_size` 与段尾。已见变体出现页对齐段和 `dexdata0` 后的短记录，但不能把对齐或记录长度当作家族常量。

同时解析类数据，找短占位 `CodeItem`、异常稀疏指令和追加尾部的真实 `CodeItem`。若当前 DEX 没有这类一一对应关系，停止套用本变体的回填模型。

## 2. 定位解密函数与密钥

沿容器读取 → 密文输入 → DEX 明文写入追踪调用链，记录实际读写范围、参数、调用时机和密钥扩展入口。可对已知输出缓冲区做窄范围写入观察，或在解析器、块变换入口/出口取输入输出向量。磁盘 SO 若只在运行时解开，捕获的代码映射可供分析，但它不是可直接加载的标准 SO；按实测地址关系在 Unidbg 中重放内层函数。

现有证据只支持以下**密钥位置结论**：039 的 Native 密钥扩展可用进程采集文件中的前 16 字节重放，但保留的记录没有证明这些字节最初来自 `libDexHelper` 静态数据区；在现存磁盘 SO 和已采集的模块 RX/RW/BSS 中也未直接搜到该原始密钥。041 的有界内存扫描曾在 `[anon:scudo:primary]` 中命中原始密钥；APK 内的磁盘 `libDexHelper.so` 未直接出现同一 16 字节序列。**两例均不足以断言密钥普遍内嵌于 `libDexHelper` 数据区。**

下次先定位 Native 密钥扩展入口，记录其 16 字节入参指针和调用时机，再反向追到真实来源。按这个数据流检查 `libDexHelper` 的静态数据及运行时 RW/BSS、独立 `[anon:.bss]`、相关堆分配、TLS 和初始化前后变化的可写映射；`[anon:scudo:*]` 只是曾命中的堆映射，不是固定地址。初次用 [`sm4_key_scan.py`](../sm4_key_scan.py) 覆盖**完整已捕获区域**，scudo 可优先但不能只扫 SO；步长 4 快筛无命中时必须在完整捕获集用步长 1 复查。扫不到时观察密钥扩展入参或静态推导派生链，不能仅凭扫描失败否定算法。

## 3. 判断算法并解密前缀

已测 `fdex` 变体的前缀符合**标准 SM4、16 字节分组、逐块独立处理（ECB）**；加密方向是 `C_i = SM4_encrypt(K, P_i)`，还原方向是 `P_i = SM4_decrypt(K, C_i)`。这描述已观察到的解密关系，未声称看到了加壳时的打包实现。先用公开向量检查本地 SM4 实现，再以当前样本的独立完整分组明文/密文对、Native 轮函数证据和多位置输出确认算法与模式。**只解出 8 字节 `dex\n` 不能证明 SM4-ECB**；相同明文块对应相同密文也只是 ECB 支持证据。具体判据见[可选 SM4/fdex 适配器](../references/sm4-fdex-adapter.zh-CN.md)。

在已验证的变体中，Native 只变换每段开头的有界前缀，后续字节从原容器保留；每段实际解密长度按 `min(DEX 文件长度, 当前样本确认的加密上限)` 向下取到完整分组。用 [`decrypt_prefixes.py`](../decrypt_prefixes.py) 导出前缀，并检查解密后的 DEX 头、完整段长和 `fdex` 尾标。**加密上限、密钥、段对齐与段数都不能从旧样本照搬。**若多位置对照不支持 SM4-ECB，回到 Native 输入输出边界，用 Unidbg 重放实际变换。

## 4. 从明文段恢复 DEX

前缀解密不等于方法还原。先将已验证前缀与同段未变换的原容器字节组合，再按当前 DEX 的 `class_data` 建立占位方法到尾部真实 `CodeItem` 的唯一映射。已见变体需要在原预留宽度内重写 ULEB128 `code_off`；[`rebuild_bangcle_fdex.py`](../../rev-dex-rebuild/rebuild_bangcle_fdex.py) 只适用于其占位特征、尾部顺序和段边界均成立的情况。要求回填方法数与最终越界 `code_off` 方法数对账，然后修复 DEX 头、用 Baksmali 反汇编全部 DEX，并抽查 JADX 中的核心业务链。残留的 `JniLib` 桥接另交 `rev-java2c` 判别。
