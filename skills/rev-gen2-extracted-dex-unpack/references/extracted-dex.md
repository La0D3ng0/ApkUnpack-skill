# Dynamic extracted DEX replay

Use this guide when a shell leaves method skeletons in the primary DEX and restores instructions, CodeItems, or `code_off` values during loading. Establish the actual mutation before choosing an `ArtMethod` model or an inner native function.

## Identify the layer

1. Run `rev-apk-shell-detect` and read `container_layout` and `routing`; static `fdex` container evidence is sufficient to enter this Skill. Hash the supplied APK. If using a device vector, also hash the installed APK and record ABI, Android version, process, and native mappings.
2. Parse the on-disk DEX or `fdex` container first. When memory evidence is needed, capture identified process mappings and compare pages and DEX sections. Retain `file_size` bytes, including data beyond `data_off + data_size`. For a native key or pointer, check module RX/RW/BSS, separate `[anon:.bss]`, the allocator mappings actually used (possibly scudo), and relevant stack/TLS. Select pages from this sample's evidence and retain address/hash provenance. A generic panda dump is not the default entry to this workflow.
3. Parse original class data and record each method's `code_off`, CodeItem header, and instruction bytes. A patterned placeholder plus a matching real CodeItem in an appended tail is stronger evidence than a small or all-`nop` body by itself.
4. Count JNI bridge calls separately. A method body that invokes a native dispatch function remains a bridge after DEX restoration. Unidbg can run that native path and reveal behavior for chosen inputs, but it does not automatically reconstruct the original Dalvik body or prove that one remains available.

`valid_data_end` is the DEX header's `data_off + data_size`, not the last parsed `map_list` item. The triage script's default `dexdata0 + 12` payload offset is an **observed candidate** for the tested variant; override it with `--payload-after-marker` and confirm the real boundary in this sample's native parser. A carved memory DEX can have stale SHA-1/Adler-32 after runtime `code_off` edits; a false header check alone does not invalidate the carve.

## Find and replay a narrow native boundary

- Use the original container bytes as input and the device mapping as the output vector. Trace strings, footer markers, callers, and writes to the changed pages. Record the native RVA, ABI, argument order, key source, exact lengths, and every memory region read.
- If the on-disk SO code is encrypted, a captured executable mapping is valid static-analysis input. It is a process snapshot, not automatically a relocatable SO. A raw unidbg mapping must place RX, RW, BSS, and table bytes at their **virtual-address offsets**. Translate only proven device GOT targets to emulated addresses. An erased section table prevents GOT lookup by section name; intact `PT_DYNAMIC`/relocations may still permit program-header analysis. A resolved IFUNC slot may point at an implementation without an exported symbol, so trace the call and pointer provenance instead of requiring a symbol name ([ELF ABI](https://refspecs.linuxfoundation.org/elf/gabi4+/ch5.dynamic.html), [glibc IFUNC](https://sourceware.org/glibc/manual/2.44/html_node/Indirect-Functions.html)). Implement a needed libc function exactly through a small SVC, or load the actual library when it resolves normally.
- Prefer the inner pure transform when the outer function requires ART internals. Construct `ArtMethod` and `CodeItem` only when the verified call actually reads them; use the target Android build's layout rather than a generic offset table.
- Pin the unidbg source revision, backend, and JDK. Run two fresh baselines. Compare the complete output range, not just DEX magic or a checksum. A successful container lookup does not prove decryption.

Keep every RVA, map range, table pointer, key source, payload offset, encrypted extent, and DEX count derived from the current APK in that sample's configuration and evidence manifest. A harness should map captured code at verified virtual offsets, repair observed pointers, invoke identified native functions, and export decrypted regions. Rediscover all entry points, arguments, and lengths for each APK. Verify the parser's payload boundary and then the decryptor output. An independent device DEX is a comparison target only, never a source of offline restoration bytes.

If independent evidence establishes standard SM4-ECB, the encrypted extent, and `fdex` segment boundaries for this sample, the [optional SM4/fdex adapter](sm4-fdex-adapter.md) can produce prefixes. Otherwise continue locating this sample's native transform; an adapter failure does not change the extracted-shell classification.

## Restore methods and validate

For the observed `fdex` variant, produce **offline prefixes before the deliverable rebuild**. `rebuild_bangcle_fdex.py` in `$rev-dex-rebuild` accepts the unmodified container, one offline-decrypted prefix per DEX, the parser-derived payload offset, and the independently established encrypted-prefix cap. Device prefixes are only for `--diagnostic-only` smoke checks or independent comparison, not deliverable input. A short DEX needs only a prefix up to its block-aligned file boundary. The adapter checks segment alignment, container ends, this variant's sparse placeholders, and ordered tail CodeItems including try/catch handlers. It rewrites only reserved fixed-width ULEB128 `code_off` fields and refuses ambiguous matches or width changes. Do not extend its signature rule to other shells without a new input/output vector.

Preserve the raw result. Create checksum-repaired copies with `repair_dex_header.py`, then use `verify_dex.py`. Successfully disassemble **every final DEX with Baksmali**, retaining its log and Smali output. Check the method map, tail bounds, class/method counts, and remaining native bridge calls. If a device reference is available, require whole-file byte equality.

Deliver the header-repaired `classes.dex`, `classes2.dex`, and later DEX files at the root of `<source-apk-filename-without-.apk>-unpacked/` inside the sample's hash-qualified workspace. There is no `classes1.dex`; the rebuild manifest records each `output_file`. Include hashes, validation, and the exact recovery scope. Decompile all recovered DEXs with a pinned JADX version, save a separate shell-DEX baseline, and record source-file counts, decompiler errors, and methods left as JNI bridges. For a roughly 90 MiB DEX set on a 16 GiB Windows host with a tight page file, start JADX near `-Xmx3g` and reduce parallelism if G1 reservation fails before blaming the DEX. Count `Method not decompiled` **methods** against all DEX methods with CodeItems: zero classes containing failed methods in the target core business packages and under 1% failed methods globally is a decompiler-quality threshold; above it, investigate. This alone does not pass a native bridge or a broken business chain. Inspect real entry, account, network, and app-specific business call chains: report readable decisions and effects, and identify paths still reduced to a native bridge. Show at least one method with readable restored logic and one native-bridge method, each traced to its original and new `code_off`. The result directory can be browsed in IDEA as ordinary Java sources.

On Windows, PowerShell 5.1 `>` may produce UTF-16/BOM and is unsuitable for raw bytes; do not rely on default text encodings across PowerShell versions. Prefer `adb exec-out` with Python writing the returned byte stream, then detect BOM/UTF-8/target encoding in Python for text. Quoting through PowerShell, ADB, and `su -c` may be stripped or reinterpreted: probe a harmless command first or stage a short script on the device, and record the actual invocation.

## Handoff to nativeized methods

Once the rebuilt DEX passes structural checks and, when available, device byte comparison, report extracted-DEX restoration complete for the validated scope. There is no mandatory next protection layer: stop when the requested business scope is restored and no relevant native bridge remains. Pass any remaining JNI bridges to `$rev-java2c` with the exact method descriptor, original/restored `code_off`, bridge signature and dispatch ID, source APK/SO hashes, and JADX or smali evidence. Classify each bridge from evidence as delayed Dalvik refill, ordinary native/JNI implementation, private bytecode VM, or unresolved behavior. A `JniLib` call by itself does not establish VMP; `$rev-java2c` hands off to `$rev-opcodes` only after the VM fetch/decode/handler chain is demonstrated.

Keep case-specific offsets, lengths, restoration counts, and business acceptance evidence in each sample's experiment report. Do not treat one APK's parameters or recovery ratio as a premise for the next APK.
